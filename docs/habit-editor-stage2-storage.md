## Scope and boundary

The accepted storage/transfer foundation adds a separately validated configuration document and portable backup v10, while retaining the exact schema-1 habit catalog. The accepted runtime integration now consumes explicit valid stored/imported consent; absent, disabled or invalid configuration remains manual. It does not yet expose new opt-in/setting/timing controls or change cue activation/provenance. Native widget schema, notification consent and physical-device data are unchanged. Runtime acceptance is separate from the earlier storage gates below.

## Isolated configuration

`CUSTOM_NEXT_WAVE_KEY = 'wavelength_custom_next_wave_v1'` stores:

```json
{"schemaVersion":1,"settings":[{"habitId":"habit_opaque_id","enabled":false,"setting":"either"}]}
```

- Only retained custom IDs, including archived definitions, are valid references. Maximum 100 unique records; exact booleans and `indoor` / `outdoor` / `either` values; no unknown fields.
- Missing/invalid configuration fails closed to an empty manual configuration. Read paths never write defaults or overwrite corrupt raw data.
- Strict validation rejects the whole invalid document rather than carrying partial consent forward. Integrity compares persisted/current normalized semantics, treating record order as nonsemantic without mutating input arrays.
- The existing schema-1 catalog and definition whitelists are unchanged. Actual previous-reader probes show that embedding unknown metadata would invalidate the entire catalog, whereas the separate key remains untouched by ordinary older catalog/seven-key save paths. An older explicit import can still leave orphan metadata; this is a fail-closed/recovery boundary, not a guarantee against every stale-reader action.

## Portable backup v10

The payload adds `customNextWave` alongside existing `habitCatalog`, state/progress, order, First Name, Insights, categories and shipped overrides.

- Valid versions 1–10 are accepted. Versions 9 and 10 both require the strict retained catalog and exact complete order; the current-version bump must not remigrate a v9 custom catalog or permit missing IDs.
- Versions 1–8 retain their deterministic legacy catalog/order/category migration. Every version 1–9 import writes canonical empty configuration atomically, never destination consent.
- A v10 document requires strict configuration referencing its imported retained catalog. Missing/null/malformed, duplicate, orphan or nonboolean records fail before journal creation or any write.
- A valid explicit import may replace corrupt current configuration. Export instead checks stored integrity and reports a visible failure rather than exporting an empty read fallback over corruption.

## Transaction and recovery

All eight authoritative documents participate in one `commitStorageSnapshot` batch. Measurement, streak and displayed prospective evidence reconciliation happen before commit against the projected imported catalogs. Runtime globals are adopted only after successful commit. The synchronous committed-snapshot render suppresses additional state/evidence persistence and restores its prior guard in `finally`; unrelated ordinary renders retain their existing behavior.

Parent browser instrumentation verifies journal creation, the eight document mutations, then journal removal, with no additional storage calls through the following 200 ms. One-shot faults at all ten mutation boundaries restore raw prior bytes and absence, including a corrupt previous configuration, without changing runtime globals.

Recovery validates the complete entry list before restoring any key. This fixes the reproduced valid-first/malformed-later partial-restoration defect while retaining arbitrary legitimate subset/seven/eight-key journals and raw previous values. The pre-existing startup exception wrapper and repeated/persistent storage-failure durability are outside this bounded correction; do not imply stronger guarantees from one-shot fault injection.
